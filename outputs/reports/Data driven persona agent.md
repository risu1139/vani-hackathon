# Log the decision now, learn later

**No public system has VANI's exact shape: a script extracts seller data, an LLM agent with tools picks a voice persona and call plan for each customer, and the system learns from outcomes. The parts do exist separately, and every outcome-learning system we found puts the learning in a statistical layer, not in the LLM.** The closest analogues are Aampe, Pega, Afiniti, Salesforce Atlas and NVIDIA's Data Flywheel. Aampe runs one agent per user over decomposed action dimensions, including a tone-of-voice dimension, with Beta posteriors and similar-user priors. Pega has eligibility rules, then propensity, then a P×C×V×L arbitration formula, and cold-starts new actions with Thompson sampling. Afiniti learns pairing outcomes nightly, excludes protected classes and benchmarks with an ON/OFF holdout. Atlas is an LLM planner over scoped tools whose improvement is configuration, not learned weights. NVIDIA's flywheel logs every agent call with a `workload_id` and leaves promotion to a human. The best version for VANI combines them. **The Sarvam LLM agent reads learned statistics through read-only tools and proposes a ranked shortlist per setting with reasons. Code applies gates, enforces evidence-backed rules, randomises inside a logged probability, keeps a holdout and writes one immutable decision row. Versioned tables (memory, Beta evidence, rules) do the learning.** The most important answer concerns data. PS07 holds **269,455 answered calls with one voice and one style**, so it can never show which voice suits which seller. Four facts exist only at the moment of decision: the as-of seller snapshot, the candidate set, the action actually executed, and the probability it had. They need a `decision_id` that joins them to delayed outcomes and to every version in play. **If these are not created from the first call, every later stage (bandits, off-policy evaluation, uplift, distillation) is impossible or biased.** Microsoft measured up to **3.0×** estimation error from wrong probabilities and **8.7×** from a decision leaking into features ([Decision Service](https://arxiv.org/abs/1606.03966)). The team lead's segment hypotheses ("₹1 Cr+ → authoritative senior voice", "rural → young warm female voice") have no direct evidence. Keep them as low-weight GUESS priors on tone, pace and formality, decoupled from voice gender. Test them only by logged randomisation, which needs thousands of calls per arm and therefore real post-event traffic.

Tags: **PROVEN** = measured by us (spikes, PS07 aggregates). **DOCUMENTED** = a paper, official doc or `raw/` source says it. **VENDOR CLAIM** = self-reported results or marketing. **ASSUMED** = our design or inference. Binding context: no model training during the hackathon. The core voice agent is Sarvam. Data stays on IndiaMART infra (git-ignored `data/`, internal gateway, self-hosted Daytona). Per-call voice override is parked. Session-start `text_to_speech_config` was **ignored** in our SDK spike: female voice, pace 0.85 vs 1.25 and pitch ±0.2 all produced the same male voice, at a median F0 of about 126 Hz (PROVEN) ([voice-override spike](../../raw/research/2026-10-08-voice-override-spike.md)). The route the docstring suggests is an on_start Code Tool, which Sarvam provides only on request. **Until then, voice and pace vary only by choosing among published agent versions (`app_version`).** Every "voice arm" below is therefore a published version, not a free parameter.

## Five patterns combine into one architecture with a single learning seam

The design method asks for the whole chain first, one fixed role per block. The figure below folds the earlier five-block persona pipeline into the agent shape the team lead proposed. It adds the two pieces that pipeline lacked: a decision log that can support causal learning, and a staged learner.

The learning seam is deliberate. **The agent decides and the tables learn.** The agent quotes posteriors that it reads through tools. It never "remembers" outcomes in free text, so a drifting prompt can never become the model. This is the common pattern across every system surveyed. Deterministic profile prep comes first, then hard eligibility, a learned scorer per action with priors and exploration, arbitration, and finally a decision log joined to delayed outcomes with a holdout to prove lift. Where an LLM appears (Atlas), it sits *on top* as planner and composer and is not the thing that learns ([industry notes](../research_notes/Data%20driven%20persona%20agent/industry_architectures.md)).

## The closest analogues each own one piece, and none owns the whole

**Aampe is the nearest published match** (DOCUMENTED, vendor-authored arXiv paper). It runs one independent agent per user. Its action space is split into modular sets — **tone-of-voice, emoji use, value proposition, incentive** — each with a per-user Beta-Bernoulli posterior sampled by Thompson sampling. Cold start uses an "empirical Bayes prior… based on behaviour from similar users". Content comes from curated catalogues, explicitly to avoid LLM confabulation. A 3-week RCT on **6.4M users** reported conversion gains of +0.07 % to +0.48 % with 99 % CIs excluding zero ([Aampe, arXiv 2506.16429](https://arxiv.org/html/2506.16429v1)). Two lessons carry over: learn per dimension rather than per full persona, and expect small effects that need very large samples.

**Pega supplies the arbitration and the cold-start prior** (DOCUMENTED). Priority = propensity × context × value × levers, computed after eligibility filtering. New actions, whose propensity is "not reliable as they would have too few or no customer responses", get Thompson-sampling noise. They also get a weighted average with a **StartingPropensity at weight 1 and StartingEvidence at weight 25**, which gives them "a fighting chance" ([Pega Academy](https://academy.pega.com/node/47811); [Pega docs](https://docs-previous.pega.com/node/2307541)). This is the exact mechanism for a team lead's hypothesis: it enters as a prior worth a few dozen pseudo-calls, and data then overrides it.

**Afiniti and Genesys are the human analogue of "which voice for which seller"** (DOCUMENTED). Afiniti predicts "the outcome of all possible caller/agent pairings" and refreshes nightly. It **excludes protected-class data** and benchmarks by cycling the AI ON and OFF through the day; the 80/20 split is a secondary VENDOR CLAIM ([Afiniti](https://www.afiniti.com/responsible-ai/how-it-works/)). Genesys predictive routing uses white-box models with **no PII and no gender or nationality**, retrains weekly and ships built-in A/B testing ([Genesys](https://help.genesys.cloud/articles/use-of-ai-in-predictive-routing/)). Both learn offline, between calls, which supports the team decision that nothing learns mid-call.

**Salesforce Atlas shows what an LLM agent in production actually does** (DOCUMENTED engineering blog). It runs a ReAct loop over topic-scoped actions with declarative configuration and guardrails. Its reported "2x increase in response relevance" is a VENDOR CLAIM ([Salesforce Engineering](https://engineering.salesforce.com/inside-the-brain-of-agentforce-revealing-the-atlas-reasoning-engine/)). We found no public evidence that it learns from outcomes automatically. Improvement there means humans editing topics and instructions. **NVIDIA's Data Flywheel supplies the logging discipline.** It records every request and response with `timestamp`, `workload_id` and `client_id`, then tests base, in-context and LoRA variants with an LLM judge. Its own warning is "a flashlight, not an autopilot", with promotion left to a human ([NVIDIA blueprint](https://github.com/NVIDIA-AI-Blueprints/data-flywheel)). Its only reported result is a cost reduction of "up to 98.6 %" (VENDOR CLAIM). Its judge measures imitation, not outcomes, so VANI must join decisions to call outcomes or it will learn to copy itself (ASSUMED).

What is missing everywhere is the composition. **We found no public production case in which an LLM agent with tools is the per-customer decider and also improves automatically from outcomes.** Statsig's contextual bandit makes the same point from the other side. It retrains hourly, strictly prefers the **explore dataset** for training and monitors random against targeted traffic ([Statsig](https://docs.statsig.com/autotune/contextual/methodology)). Learning needs logged randomness. If the agent always gives a rural seller the same voice, the system can never learn whether that was right.

## The decision layer: the agent ranks with tools, and code gates, explores and logs

Our own test settles the agent's role. On six synthetic sellers, rules in code plus one Sarvam wording call got **23/23** key decisions right. One LLM call deciding the settings got **16/23**, and validator-driven revisions reached only **17/23**. The wrong decisions came with plausible false reasons that no validator caught (PROVEN) ([options test](../research_notes/Persona%20generator%20architecture/vani_options_test.md)). The literature agrees. LLMs "cannot self-correct reasoning yet" without external feedback ([Huang et al.](https://arxiv.org/abs/2310.01798)). In bandit tasks only one configuration explored adequately: GPT-4 with chain of thought **and an externally summarised history given as sufficient statistics**. Others stuck to the most recent option or behaved uniformly ([Krishnamurthy et al.](https://arxiv.org/abs/2403.15371)). An "agent with tools" therefore earns its place as a **ranker that reads summarised evidence**, not as the final policy.

The tension with the team lead's design is real and needs naming. If the LLM picks one persona deterministically, every logged propensity equals 1. Off-policy evaluation of any other policy is then impossible, and the agent's choice is perfectly confounded with the segment (DOCUMENTED principle: importance weighting needs a nonzero logging probability wherever the new policy acts ([Bottou et al.](https://arxiv.org/abs/1209.2355))). Sampling temperature does not fix this, because the probability of the resulting persona is unknown and unlogged (ASSUMED). The resolution keeps both goals. The agent is explainable for judges, and the data is usable for learning.

| Step | Owner | What happens | Logged as |
|---|---|---|---|
| 1. Gather | Agent → tools | `get_seller_context`, `get_seller_memory`, `get_rule_table`, `get_voice_options`, optional `get_segment_stats` / `find_similar_sellers` | `tool_calls[]` with args hash, result ref, latency |
| 2. Rank | Agent | Per setting (voice profile, language start, formality/warmth/brevity, opening move, objection order): ranked candidates with score, reason, rule id; plan move ids from the library | `candidates`, `agent_choice`, `reasoning_summary` (≤300 chars) |
| 3. Gate | Code | Remove ineligible options: DNC (no call), language without catalogue voice, unpublished `app_version`, guardrail-violating plan moves | `gates_applied[]` |
| 4. Enforce | Code | STRONG/MODERATE rules are binding. If the agent's top pick contradicts one, code overrides and logs the disagreement. The agent's ranking decides only GUESS/WEAK settings and ties | `binding_overrides[]` |
| 5. Explore | Code | Hackathon: ε-greedy around the agent's top pick on at most 1–2 settings (voice profile, opening move), ε ≈ 0.1–0.2, floor per eligible arm. Later: Thompson draw per (segment × setting) with the agent's ranking as a small-weight prior | `explore{policy, ε, seed}`, `propensity{per setting, joint}` |
| 6. Holdout | Code | Fixed fraction (e.g. 10–20 %) gets the default persona, Afiniti-style | `arm_type: agent / explored / holdout` |
| 7. Validate + compile | Code | Seven validators, one repair call, template fallback; voice resolved to `app_version` | `validator{passed, repairs}`, `spec_hash` |

Step 4 keeps the 23/23 result. Step 2 lets the agent contribute where rules are silent: plan composition, ordering and GUESS-tier choices. Step 5 creates the first voice variation VANI has ever had. Because the agent ranks and code samples, the propensity of the executed action is exact (ASSUMED design; the research notes call this split "our design", since no cited system logs an LLM-agent policy) ([data design notes](../research_notes/Data%20driven%20persona%20agent/data_design.md)). For a Thompson draw, the propensity can be estimated by repeating the posterior draw many times with the logged seed (ASSUMED). On the judged demo seller, exploration and holdout are switched off and logged as such.

**The voice arm under the parked override.** The SDK override is ignored and Instant Outbound accepts no TTS override (PROVEN/DOCUMENTED) ([voice-override spike](../../raw/research/2026-10-08-voice-override-spike.md)). A voice arm is therefore one of a few published agent versions per language, each fixing speaker, pace and gender. Coverage is uneven: Tamil has only 3 male v4 voices, and Gujarati has 2 female and 1 male (PROVEN, catalogue) ([persona generator report](Persona%20generator%20architecture.md)). The arm count stays small, which suits learning. But voice and pace are bundled, so their effects cannot be separated until per-call override arrives (ASSUMED). Every call must log `app_version_requested` and a `voice_observed` check. The spike already showed a cheap one: median F0 separates the male band (~85–155 Hz) from the female band (~165–255 Hz) on the recording (PROVEN technique).

## The data layer: six records, one key, and four facts that cannot be backfilled

The Decision Service rule is the backbone: record (context, action, probability) **at the time of decision** and match the reward later. Its named failure modes all apply here. Features stored as references to rows that a separate process later updates. Actions overridden downstream, so the logged probability belongs to a different action. Probabilities leaking into features by accident ([Decision Service](https://arxiv.org/abs/1606.03966)). Azure Personalizer productises the same idea with an `eventId` per Rank call that a later Reward call joins on ([Azure Personalizer](https://learn.microsoft.com/en-us/dotnet/api/azure.ai.personalizer)). VANI's equivalent is a `decision_id` (UUIDv7) minted before compile and passed into Sarvam inside `agent_variables`. Every tool call to the signal server then carries it back (ASSUMED). Whether Sarvam echoes it in every tool payload is untested.

| Record | Key | Written by | When | Load-bearing fields | Consumed by |
|---|---|---|---|---|---|
| `seller_snapshot` | `snapshot_id`, `seller_key`, `as_of` | D1 | Before decision; immutable | profile bands, engagement, `history_as_of_t`, flags, `missing_fields`, `completeness`, `extract_version` | All stages; leakage-free replay; nearest neighbours as they were |
| `decision` | `decision_id` | D3 wrapper only | Before dial; immutable | `versions{agent_model, prompt, tool_schema, rule_table, voice_catalogue, compiler, switcher, git_sha}`, `tool_calls`, `candidates`, `agent_choice`, `gates_applied`, `binding_overrides`, `explore`, `final_action`, `propensity`, `arm_type`, `spec_hash` | Stage 1 tables; Stage 2 bandit/OPE; Stage 3 distillation |
| `call` | `call_id` (Sarvam), `decision_id` | D5 + Sarvam fetch | End of call | `app_version_requested`, `voice_observed`, `pace_requested`, duration, answered/IVR, `turns_ref`, `switch_log[]`, tool-call dupes, latency, `plan_followed` | Switch learning; voice-mismatch audit; reviewer |
| `outcome` | `decision_id`, `kind`, `observed_at` | Joins | Appended as events arrive | in-call disposition, `meeting_fixed`, `dnc_requested`, next-call disposition within window, `exec_contact_7d` confound, reviewer fit, human ratings | Reward function; all learners |
| `review` | `review_id`, `decision_id` | D6 | Post-call | per-setting `persona_fit`, switch verdicts, signals, `reviewer_model`, `prompt_version`, `causal_claim_allowed` | Evidence updates; reviewer κ tracking |
| `rule_table` / hypothesis register | `rule_id`, `version` | L1 + humans | Each run | segment key, setting, level, `alpha`, `beta`, `n_eff`, tier, `source` (ps07_mined / reviewer_pooled / design_prior), `time_split_ok`, pre-registered metric and direction | D2 tools; D3 binding rules and priors |

`seller_memory` is a derived view recomputed from these rows and never hand-edited. It is bi-temporal (`valid_from`, `invalid_at`), so a newer language preference supersedes an older one instead of averaging with it. State facts decay with a half-life of about 20 days. Traits such as rush, terse or English-heavy are Beta posteriors shrunk to the segment rate (PROVEN counts, ASSUMED fit) ([between-run report](Between%20run%20learning%20loops.md)).

**The reward is a declared function, fixed in advance.** An example is "meeting fixed in call, or a positive next call within 14 days, with no DNC request". It has a fixed join window and a default of 0. A fixed window is how Decision Service avoids bias from rewards that arrive at different delays for different actions (DOCUMENTED) ([Decision Service](https://arxiv.org/abs/1606.03966)). The reward should be typed, because a meeting-only reward can be gamed by a pushy plan that also raises complaints (ASSUMED).

**Storage.** Use append-only JSONL, compacted to Parquet partitions under git-ignored `data/vani_store/events/`. DuckDB views provide `v_seller_features_asof`, `v_seller_memory_asof`, `v_segment_stats`, `v_decision_outcome` and `v_training_examples`. A `versions/manifest.jsonl` maps each version id to a content hash and git sha (ASSUMED). The property that matters is point-in-time correctness: for each (entity, timestamp), use the latest value valid at or before it. That is the reason feature stores exist ([Feast](https://docs.feast.dev/v0.22-branch)), but no feature-store product is needed at this scale. PS07 alone is **149,363 sellers, 269,455 answered calls and 12,788 transcribed calls** (DOCUMENTED) ([data dictionary](../../raw/hackathon/2026-10-07-ps07-persona-data-dictionary.md)). Move to an internal Postgres or warehouse only when live traffic brings multiple writers. Erasure under DPDP s.8(7) is practical because every view rebuilds from the events ([DPDPA s.8](https://dpdpa.com/dpdpa2023/chapter-2/section8.html)). Anything that leaves `data/` uses a salted `seller_key` hash, category ids and aggregates only.

**Agent tools.** All tools are read-only and return provenance (`as_of`, `source_version`, `n`). The agent never writes to the store.

| Tool | Input | Output | Day one? |
|---|---|---|---|
| `get_seller_context` | `seller_key`, `as_of` | Snapshot + `missing_fields` + `completeness`; writes the snapshot row; the agent may cite only these fields | Must |
| `get_seller_memory` | `seller_key`, `as_of` | State items with recency weight, trait posteriors (mean, n), `lang_pref`, `dnc` | Must |
| `get_rule_table` | `setting`, `segment` | Rules `{rule_id, level, tier, alpha, beta, n_eff, reason_template}`, table version | Must |
| `get_voice_options` | `language`, `channel` | Published `app_version`s `{profile_id, speaker, gender, timbre_tag, pace}` for that language | Must |
| `get_plan_library` | `move_type` | Approved opening/step/objection/escalation ids + templates | Must |
| `get_segment_stats` | Coarse segment dict, metric | Rate, Beta interval, n, time-split flag, tier | Nice-to-have |
| `find_similar_sellers` | `seller_key`, `as_of`, `k ≤ 20` | Aggregates of neighbours' past persona + outcome + review fit, `ts < as_of` only, no transcript text | Nice-to-have |
| `propose_persona` (terminal) | Ranked candidates per setting with reasons | Handed to D3 | Must |

Tools return summary statistics (n, rate, interval), not raw histories. That is the one configuration Krishnamurthy et al. found to explore well, and it blocks the recency and "vivid case" bias of raw transcripts ([Krishnamurthy et al.](https://arxiv.org/abs/2403.15371)).

## Four learning stages turn the same rows into progressively causal answers

PS07's structural fact governs everything. **It has zero variation in voice, tone and pace, so it can show which sellers convert and which in-call signals predict outcomes, but never which persona works for which segment** (ASSUMED; this is the positivity requirement). Bot-version assignment was also non-random: **87.4 %** of a seller's consecutive calls used the same version, and **97 % of Tamil Nadu** sellers got `arrowhead` (PROVEN) ([between-run report](Between%20run%20learning%20loops.md)). Backfilled PS07 rows must therefore carry `run_type=ps07_replay`, `propensity=null` and `causal_claim_allowed=false`. Power arithmetic sets the volumes (ASSUMED; two-sided α 0.05, 80 % power). Telling a 10 % meeting rate from 15 % needs about **680 calls per arm**. Telling 10 % from 13 % needs about **1,770**. Telling 10 % from 12 % needs about **3,800**. Multiply by the number of segments that need separate answers.

| Stage | When | Data it reads | Minimum volume | Can learn | Cannot learn | How the day-one rows are used |
|---|---|---|---|---|---|---|
| **0 Priors** | Hackathon (9–10 Oct) | Snapshots, PS07 aggregates, catalogue, rule table, hypothesis register | None to decide; n ≥ 200, CI excluding 0 and a time split to mine a PS07 rule | Seller-side rules (language, brevity after rush, objection order, escalation), per-seller memory | Any voice/tone/gender effect | Snapshot + decision rows prove the reasons and tiers in each spec; the rule table is the evidence deliverable |

| **3 Distillation / fine-tuning** | 6+ months; needs GPU or provider fine-tuning | `v_training_examples`: snapshot, tool results, final spec, reward, propensity, versions | Tens of thousands of outcome-labelled calls (ASSUMED; no source found) | A smooth decision policy over many features; better wording | Anything outside the logged support | IPS-weighted training of a small policy model; KTO on binary call outcomes; SFT on high-reward, guardrail-clean trajectories |

**Stage 0** must label every delivery choice honestly. The strongest PS07 lever is the seller's own history: next-call meeting AUC is **0.71 for memory against 0.58 for profile**, and next-NI AUC is 0.78 against 0.54 (PROVEN) ([learning loops](../../wiki/projects/vani-hackathon/learning-loops.md)). LLM-generated priors cut early bandit regret by **14–20 %** when aligned ([arXiv 2406.19317](https://arxiv.org/html/2406.19317v2)). Under systematic misalignment they can do **worse than a cold start** ([arXiv 2604.02527](https://arxiv.org/abs/2604.02527)). A confident LLM rationale for a stereotype is therefore a liability, not a prior.

**Stage 1** is in-context learning from experience. It works on verifiable tasks. Agent Workflow Memory reported +24.6 % and +51.1 % relative success on Mind2Web and WebArena ([AWM](https://arxiv.org/abs/2409.07429)). ExpeL improves as experience accumulates, without parameter updates ([ExpeL](https://arxiv.org/abs/2308.10144)). LaMP showed that retrieving a user's *own* past items helps every personalisation task ([LaMP](https://arxiv.org/abs/2304.11406)). GEPA beat GRPO by 6 % on average with up to 35× fewer rollouts, so it suits wording prompts that have an external metric ([GEPA](https://arxiv.org/abs/2507.19457)). None of these were tested on sales calls with noisy, delayed binary outcomes. Their main risk is self-reinforcement: the agent retrieves its own past choices as "evidence". Feedback loops of this kind homogenise behaviour without raising utility ([Chaney et al.](https://arxiv.org/abs/1710.11214)).

**Stage 2** is the only stage that answers the team lead's question causally. Thompson sampling with uncertainty beats greedy LLM policies on real contextual-bandit data ([Felicioni et al.](https://arxiv.org/abs/2404.02649)). Doubly robust estimation is accurate if either the reward model or the propensities are right ([Dudík et al.](https://arxiv.org/abs/1103.4601)). Clipped importance weights expose "domains poorly explored", which serves as a "need more exploration" flag ([Bottou et al.](https://arxiv.org/abs/1209.2355)). Netflix artwork and Spotify BaRT both evaluate offline by replay with propensity correction (DOCUMENTED, secondary) ([QCon slides](https://qconsf.com/sf2018/system/files/presentation-slides/2018-11_-_qcon_artwork_personalization_talk.pdf)). One warning matters for VANI. In an off-policy evaluation of a real LLM coaching agent, a policy that raised average value **harmed specific subgroups**. The authors recommend freezing the generator, learning subgroup-aware decision heads and always reporting per-archetype metrics ([arXiv 2510.17173](https://arxiv.org/abs/2510.17173)).

**Stage 3** comes last and trains the cheapest thing first. Distil the decision policy into a small, auditable model on IPS-weighted randomised logs. Then consider KTO, which aligns from binary desirable/undesirable labels such as "meeting yes/no" ([KTO](https://arxiv.org/abs/2402.01306)). The persuasion literature adds a hard caution. In a 76,977-participant study, post-training raised persuasiveness by up to **51 %** while the most persuasive models were the **least accurate** ([Hackenburg et al. 2025](https://arxiv.org/abs/2507.13919)). The core in-call agent is Sarvam, and Sarvam agents do not take our own LLM, so in-call fine-tuning depends on Sarvam offering it. The decision model and offline wording generator can be ours.

## The team lead's segment hypotheses survive only as low-weight, gender-neutral priors

The direct answer is that **PS07 cannot test any voice hypothesis**. VANI used one voice, and PS07 has no bot-voice or seller-gender column. Every gender choice is therefore GUESS by construction (DOCUMENTED) ([learning loops](../../wiki/projects/vani-hackathon/learning-loops.md)). The outside evidence is thin and points away from demographic tailoring. GPT-4 microtargeted political messages were **not statistically more persuasive than non-targeted ones** ([Hackenburg & Margetts, PNAS 2024](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11181035/)). In the 76,977-participant study, personalising to age or politics gave a **negligible** boost ([arXiv 2507.13919](https://arxiv.org/abs/2507.13919)). The steelman counterpoint is live multi-round debate, where sociodemographic personalisation gave GPT-4 81.7 % higher odds of shifting agreement ([Salvi et al., Nature Human Behaviour 2025](https://www.rivista.ai/wp-content/uploads/2025/05/s41562-025-02194-6.pdf)). That setting is an interactive argument, not a two-minute sales call. IndiaMART's own three static-personalisation trials **did not beat control** (PROVEN) ([between-run report](Between%20run%20learning%20loops.md)).

On voice itself, the best study is small and foreign. It had 335 US participants, synthetic Microsoft voices and self-rated purchase likelihood. Tone mattered most: positive tones had a large effect and neutral a medium effect over negative. Gender × age had only a **small** effect, with middle-aged male and younger female voices ahead, and older voices were dropped because listeners could not tell ages apart ([arXiv 2405.04791](https://ar5iv.labs.arxiv.org/html/2405.04791)). A University of Michigan analysis of 1,380 telephone survey introductions favoured a **moderate rate (~3.5 words/s)**, natural pauses and lower median pitch. Perfectly fluent delivery did worst ("too scripted") (DOCUMENTED, secondary summary) ([ScienceDaily](https://www.sciencedaily.com/releases/2011/05/110515122507.htm)). An analysis of AI voice-phishing calls found that script persuasiveness, not the voice, drove compliance (DOCUMENTED, news summary) ([Help Net Security](https://www.helpnetsecurity.com/?p=377915)). None of this evidence comes from India, from Hindi or regional languages, or from B2B sellers.

Industry draws a clear line on protected attributes. Afiniti excludes protected-class data, and Genesys uses no gender or nationality ([Afiniti](https://www.afiniti.com/responsible-ai/how-it-works/); [Genesys](https://help.genesys.cloud/articles/use-of-ai-in-predictive-routing/)). VANI chooses the *bot's* voice and never infers the seller's gender, so turnover band and location are legitimate features. Tying a female voice to "rural" is a different matter. It encodes the pattern UNESCO criticised in female-by-default assistants, which cast women as "obliging, docile and eager-to-please helpers" ([Dezeen on UNESCO 2019](https://www.dezeen.com/2019/05/24/united-nations-voice-assistants-gender-biases-siri-alexa/)). A bandit seeded with that prior can harden it into policy. And persona-fidelity models are documented to produce the most stereotyped populations ([arXiv 2604.24698](https://arxiv.org/abs/2604.24698)).

| Hypothesis | Evidence | Keep as | Apply how |
|---|---|---|---|
| ₹1 Cr+ → authoritative senior voice/tone | Indirect, weak support for *delivery* (lower pitch, moderate pace, crisp formal tone trusted); none for gender; "senior" age is barely perceptible in synthetic voices | **GUESS prior on formality/brevity/pace profile**, voice-gender-neutral | `rule_table` row with `source=design_prior`, tier GUESS, Beta prior worth ~10–25 pseudo-calls (Pega StartingEvidence = 25 as reference); never binding; explored with a floor; `annual_turnover` band as segment key |
| Rural → young warm female voice | No direct evidence; the one gender × age result is US, synthetic, small-effect; stereotype and fairness risk | **Do not ship as a rule.** Split it into "warm tone, slower pace, simpler words, regional language" for sellers whose *own* history shows confusion or low familiarity (PS07-backed), and leave gender to catalogue coverage + rotation | If the team lead insists, register "warm vs neutral timbre" as a pre-registered hypothesis tested with gender-balanced arms; audit allocation and alarm at >80 % one-gender skew per segment |
| Language match, per-seller memory, positive/neutral tone, moderate pace | PS07 memory AUC 0.71; LaMP; tone and pace studies | MODERATE/STRONG (language, memory); WEAK (tone, pace) | Binding where STRONG/MODERATE; ranked by the agent where WEAK |

"Rural" is not a PS07 field. The data dictionary offers `seller_city`, `seller_district`, `seller_pincode` and `seller_locality` ([data dictionary](../../raw/hackathon/2026-10-07-ps07-persona-data-dictionary.md)). A rural flag would need a pincode-to-urban/rural mapping that we have not sourced (ASSUMED). The hypothesis register should record each guess with a predicted direction, metric, minimum n and review date. A wrong guess is then retired by data, not by argument.

## Devil's advocate

**PS04 never scores learning.** The weights are fit 25, switches 25, distinctness 20, natural voice 15 and evidence 15. The build budget is already tight at ~20–30 dev-hours of core work against ~18–24 usable ([learning loops](../../wiki/projects/vani-hackathon/learning-loops.md)). The steelman is to skip the data layer and build the demo. The answer is that the must-have rows cost a few columns and one sampling step. They also produce the evidence table and the reasons that the 15 % evidence criterion scores. Everything else is cut first.

**The "agent" may be decorative.** Rules plus one wording call scored 23/23. The agent adds latency and cost, and it can introduce false reasons. If binding rules cover most settings, the agent decides little. The case for keeping it: it composes plans, ranks GUESS settings, gives judges a legible tool trace, and becomes the natural home for Stage 1 retrieval. But it must stay a ranker. Note also that the 23/23 is circular, because the labels came from the same toy table, and the real rule table has not yet been mined.

**Exploration on real sellers is deliberately non-optimal.** Organiser rules on it are unknown. The expected cost is small at ε ≈ 0.1 over GUESS-tier settings, where the "optimal" choice is itself a guess. It must still be disclosed and kept off the judged seller.

**Two days of data teach nothing causal.** With 30–60 reviewed calls, only ~20-point differences are visible, and κ has a ±0.26 interval at n = 30 ([learning loops](../../wiki/projects/vani-hackathon/learning-loops.md)). The honest claim is "the system logs what is needed for that claim once VANI runs live", not "it learned which voice works".

**Per-dimension learning assumes the dimensions do not interact.** Gender × tone interactions are untested anywhere public. And bundling voice with pace in each `app_version` already fuses two dimensions.

**LLM reviewers are biased labellers.** Self-preference and sycophancy are documented. PS07 evaluator labels agreed with our lexicon at only κ ≈ 0.03 (PROVEN). Hard outcomes and human-checked samples must anchor the reward.

**The whole later path depends on a decision we do not control.** It pays off only if IndiaMART routes live VANI traffic through this agent after the event.

## Conclusion

The question "does this architecture exist?" has a sharper answer than yes or no. Every component exists in production, but no one has published the composition. The industry consensus is also clear on where the LLM goes: on top, reading statistics and composing, never as the learner. VANI's design then becomes a logging problem more than a modelling problem. An agent that ranks and code that samples turns an explainable LLM decision into a dataset that bandits, off-policy evaluation and distillation can use. That conversion is only possible at the moment of the call. PS07's 269K calls show what happens otherwise: a large archive that cannot answer the one question the team lead most wants answered.

The segment hypotheses change status under this design. They stop being rules to argue about and become registered, low-weight priors with a stated metric and minimum n. They are decoupled from voice gender and exposed to randomisation that can retire them. The parked voice override narrows the near-term voice question to a choice among a few published versions. That is a small, learnable action space, and it is a reason to start logging exploration over it as soon as live traffic exists rather than waiting for per-call control.
