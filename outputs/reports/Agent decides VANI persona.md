# Let the agent decide, let code guard

## Summary in simple words

1. This report compares two ways to select each seller's VANI persona.
2. A VANI persona is VANI's voice, speed, tone, language and call plan. Seller data is the input.
3. In Design L, the team lead's design, an AI agent gets the seller's traits and states and the candidate personas.
4. The agent uses tools to read real data. Then the agent decides the persona and the plan.
5. In Design L, the agent also says "no good fit" when no persona fits. These signals start new personas.
6. In Design V2, our plan, code selects a first persona from data. The agent proposes small changes. Code accepts or rejects each change.
7. In V2, a separate weekly agent job proposes new personas. A human approves them.
8. Design L is better when free-text call notes change the correct answer. An agent can read those notes. Code cannot.
9. Design V2 is better for structured data, for learning, for cost and for audit.
10. Research shows that production systems keep code checks around the agent.
11. Research shows that an AI's own confidence is too high. Do not use it as a gate.
12. Research shows that "none of these fit" answers from an AI are wrong in both directions.
13. Thus, we recommend a merged design. The agent decides. Code builds the fence around the decision.
14. Code makes the list of allowed personas. The agent then scores each allowed persona and selects one.
15. Code checks that each reason quotes real data. The agent runs three times. The three runs must agree.
16. Code, not the agent, adds a small random choice for learning. Code records the exact probability.
17. Code computes "no good fit" from three signals. The signals are agent agreement, distance from known sellers, and poor results.
18. Each week, a job groups the "no good fit" reasons. A human approves each new persona.
19. We do not use a rule table as a part. Rules only give starting values to the estimates.
20. A fair test on about 40 made-up sellers can decide between the designs in one afternoon. Write the correct answers before you run any design.

**The better architecture is neither pure Design L nor pure V2, but a merge in which the agent holds the pen and code holds the fence.** Design L is right about who should decide. The only input that changes a VANI persona and that code cannot read is free-text history ("my son handles this now", repeated price objections), and only an LLM agent reads it. Design V2 is right about everything around the decision. The 2025–26 evidence is consistent here. Production agents run inside deterministic guards (Salesforce, Sierra, Decagon, BCG's next-best-action stack). Verbalised confidence is inflated: in one 265K-sample study, answers stated at confidence ≥ 0.8 were wrong 48% of the time. LLM "none of the above" judgements fail both ways, with 30–50% accuracy drops when NOTA is correct, and over-abstention when an "unknown" option is offered. An agent's decision has no usable logged probability unless code draws it. The merged design keeps the team lead's intent intact: the agent, with tools, scores and selects the persona and writes the plan. It adds six evidence-backed safeguards. These are a code-computed eligible set, a cited-evidence validator, a 3-run agreement gate, a code-sampled exploration draw with logged probability, a computed (not self-reported) no-good-fit signal, and a weekly clustering job with human approval for new personas. No rule table appears as a component. Rules only seed the trait estimator and the scoreboard priors. The choice between "agent selects" and "agent edits a baseline" comes down to one testable effect, anchoring. A pre-registered 40-seller experiment on synthetic sellers settles it before the end of day 1. The experiment needs labels written before any arm runs and a stratum where free text changes the answer.

Evidence tags: **PROVEN** = measured by this team (spike or PS07 aggregate). **DOCUMENTED** = a paper, vendor doc or project `raw/` source says it. **VENDOR CLAIM** = self-reported or marketing. **ASSUMED** = our design, inference or arithmetic. No customer data is used in this report; PS07 figures are aggregates only.

## Bounded, the two designs differ only in default and anchoring

The two designs are closer than their framing suggests. Design L gives the agent the seller's traits and states, the candidate VANI personas and tools: call history including free-text summaries and objections, seller memory, a seller-type × persona scoreboard, the persona library and voice options. The agent decides the persona and plan, and at decision time it emits "no good fit, because …" signals that drive new-persona creation ([agent-as-decider notes](../research_notes/Agent%20decides%20VANI%20persona/agent_as_decider.md)). Design V2 builds code candidates from trait/state estimates and the scoreboard, runs a nightly agent ("Task A") that ranks personas and writes the plan, then applies code validators and a logged arm draw. A separate weekly agent ("Task B") proposes new, merged, split or retired personas from `no_good_fit` rows and the scoreboard, and a human approves them ([plan v2](../plans/VANI%20persona%20architecture%20plan%20v2.md)).

The agent-as-decider notes found that once **the eligible set is computed by code, the fallback is a data-backed code path, and every override must cite a tool result a validator can re-check, "L-bounded and V2 converge"** (ASSUMED). Two real differences remain. First, *the default*. In L the agent's choice executes unless a gate fails. In V2 the code baseline executes unless the agent's change passes. Second, *anchoring*. V2 shows the agent a baseline to edit, which tends to cut overrides and raise precision but can suppress valid free-text-driven changes. L shows no anchor, which tends to give more overrides at lower precision. No published study compares "choose from a set" against "edit a baseline" framings on decision quality, so this effect is ASSUMED and must be measured ([agent-as-decider notes](../research_notes/Agent%20decides%20VANI%20persona/agent_as_decider.md)).

| Dimension | Design L (team lead) | Design V2 (plan v2) | Merged design (recommended) |
|---|---|---|---|
| **Who decides** | Agent, final authority | Code baseline; agent proposes bounded changes; code accepts or rejects | Agent selects persona + plan from a code-computed eligible set; code executes it unless a gate fails |
| **Inputs** | Traits, states, candidate personas, free text | Trait/state estimates, scoreboard, library; free text via agent | Same as L, with stats tools returning n, CI, p_best (not raw rows) |

| **Logging / learnability** | Agent's pick has unknown probability (stochastic, unlogged) | Code draw logs exact propensity; holdout; versions | Code draw over the agent's scores logs exact p; all k runs, citations and gate results in the decision row |

| **Cost / latency (nightly batch)** | ~₹0.3–0.6 per seller per run, 8–15 s; ~₹1–2 at k=3 | ~₹0.05–0.2 per seller; under 1 h per day | ~₹0.5–1 per seller at k=3 with pre-fetched tools; only for sellers due a call whose inputs changed |

Cost rows draw on earlier measured Sarvam-105b costs: about ₹0.16 and 4.2 s for one structured call, and about ₹0.30 and 7.6 s for a draft plus two revisions (PROVEN). The per-design figures above are ASSUMED extrapolations ([agent-as-decider notes](../research_notes/Agent%20decides%20VANI%20persona/agent_as_decider.md)). At an assumed 40K sellers due per day, which is not a measured cadence, unrouted Design L at k=3 costs ₹40K–80K and 5–8 h of batch time at 20-way concurrency, against ₹2K–8K and under an hour for V2 (ASSUMED). A nightly batch removes latency as an objection. Throughput and rate limits, not money, are the binding constraint.

## Free text is Design L's whole edge; structure, learning, cost and audit belong to V2

**Design L is better where free-text history changes the answer.** BCG's 2026 account of next-best-action systems puts the agent's value in exactly this place: "The agent doesn't replace the bandit; it decides when to defer to the bandit's quantitative recommendation and when to override it because unstructured context has changed the calculus" ([BCG](https://www.bcg.com/publications/2026/the-science-behind-next-best-action-programs)). Netflix's 2026 LLM ranker operates over "verbalized user histories and context" and reported statistically significant online gains in a large A/B test ([arXiv 2608.10257](https://arxiv.org/abs/2608.10257)). A real-estate LLM re-ranker gave **+5.3% relative CTR** and **+4.8% scheduled visits** in a randomised test, at +4.2 s latency and about +7% cost (DOCUMENTED, figures from search snippet) ([arXiv 2607.14835](https://arxiv.org/pdf/2607.14835)). Design L also has two structural advantages. It does not anchor the agent on a baseline, so a seller whose notes say "spoke to my son, he handles it" can move to a different opening without first arguing against code. And it captures the *reason* for a misfit at the moment of decision. Distance-based detectors cannot express a reason such as "needs Tamil and a slower pace; no persona offers both" ([new-persona signal notes](../research_notes/Agent%20decides%20VANI%20persona/new_persona_signals.md)). For judges, an agent that visibly reads a seller's history and chooses is also a stronger "persona per seller" story than a lookup.

**Design V2 is better on structured signal, learnability, cost and audit.** On tabular prediction, gradient-boosted trees beat LLMs once there are more than a few examples, and TabLLM wins only at 8 shots or fewer ([arXiv 2411.04324](https://arxiv.org/html/2411.04324v1)). VANI's strongest pre-call signal is structured: seller memory predicts the next-call meeting at **AUC 0.71 against 0.58 for profile** and next-call NI at 0.78 against 0.54 (PROVEN) ([Data driven persona agent report](Data%20driven%20persona%20agent.md)). Seller history sets odds, not identity: rush recurs in **30.8% of next calls against a 20.8% base**, so about seven in ten prior rushers arrive calm (PROVEN) ([translation and library report](VANI%20persona%20translation%20and%20library.md)). An agent that over-reads one rushed call does harm that a Beta posterior does not. On learnability, an agent's pick is stochastic with unknown probability. The same agent on identical input produced **2.3–4.2 distinct action sequences per 10 runs** ([ICML 2026](https://icml.cc/virtual/2026/74530)). That is the worst case for off-policy evaluation: randomness with no logged propensity (ASSUMED implication). On audit, V2 replays exactly from a snapshot, and a judge asking "why this persona?" gets n, interval and the cited field.

The earlier in-house result that rules in code scored **23/23** key decisions against **16/23** for an LLM decider must not be used against Design L. Its labels came from the same toy rule table, and its sellers had no free text, so it never tested L's only claimed edge ([plan v2](../plans/VANI%20persona%20architecture%20plan%20v2.md)). The real open question is empirical: **what share of sellers due a call carry free text that changes the right persona?** PS07 aggregates can measure this (share of calls with a non-empty objection or summary) without exposing content. It is not yet measured ([agent-as-decider notes](../research_notes/Agent%20decides%20VANI%20persona/agent_as_decider.md)).

## Five findings say the agent's own confidence cannot be the gate

**Production systems keep deterministic guards around agent decisions.** Salesforce introduced Agent Script in October 2025 to separate deterministic execution from LLM reasoning, "ensuring the agent follows a precisely defined structure … while still using LLM reasoning where judgment and contextual interpretation are needed" ([Salesforce](https://developer.salesforce.com/blogs/2025/10/introducing-hybrid-reasoning-with-agent-script)). Its argument against prompt-only control is blunt: "a 5% failure rate for something like order returns is a dealbreaker" ([Salesforce](https://salesforce.com/blog/doomprompting/)). Sierra uses "non-model checks that can't be talked out of doing their job" plus supervisor agents that audit every action ([Sierra](https://sierra.ai/blog/enterprise-grade-agents)). BCG's next-best-action stack treats propensity, bandits and agent reasoning as "additive, not alternative", with batch-computed policies as guardrails ([BCG](https://www.bcg.com/publications/2026/the-science-behind-next-best-action-programs)). The September 2026 developer discussion says the same: "The LLM is one executor inside the harness, not the harness itself" ([muffin-agent #605](https://github.com/muffin-project/muffin-agent/issues/605)). One analysis of 14 production agent workflows found 65% of nodes run as pure code (DOCUMENTED, search snippet only) ([Tom Tunguz](https://tomtunguz.com)). We found **no public A/B test in which an LLM agent alone chose a per-customer treatment against a rules or ML baseline in outbound sales or voice** ([agent-as-decider notes](../research_notes/Agent%20decides%20VANI%20persona/agent_as_decider.md)).

**LLM self-confidence is inflated, and tools only partly fix it.** Verbalised confidence is "moderately overconfident" ([Xiong et al.](https://arxiv.org/abs/2306.13063)). Older models show ECE above 0.377 with predictions clustered at 90–100% whatever the accuracy, though careful prompting brought large models near 0.07 (DOCUMENTED, secondary) ([arXiv 2405.02917](https://arxiv.org/html/2405.02917v1)). Across 265K samples and 53 runners, agreement and correctness correlated only weakly (Spearman 0.20–0.59). Answers at confidence ≥ 0.8 were **wrong 48%** of the time on GPQA Diamond, and **28% of cases were confidently wrong across all runners** ([alphaXiv 2607.08065](https://www.alphaxiv.org/abs/2607.08065.md)). Tool use cuts both ways. "Evidence tools … systematically induce severe overconfidence due to inherent noise in retrieved information, while verification tools … can ground reasoning through deterministic feedback" ([arXiv 2601.07264](https://arxiv.org/abs/2601.07264)). For VANI, the scoreboard and statistics tools are verification-like. **Free-text summaries are evidence-like**, so the one input that justifies the agent is also the one most likely to cause confident over-reading (ASSUMED application).

**"None of the above" is unreliable in both directions.** Across 28 LLMs, making NOTA the correct MMLU answer caused a consistent **30–50% performance drop** regardless of scale ([arXiv 2503.01550](https://www.arxiv.org/abs/2503.01550)). Adding an explicit "Unknown" option produces "abstention inflation", with refusals on questions the model can solve ([arXiv 2507.16199](https://arxiv.org/abs/2507.16199)). Out-of-scope intent detection degrades as the label set grows and scopes broaden, while representation distances improve it by more than 5% ([arXiv 2410.01627](https://www.alphaxiv.org/abs/2410.01627)). A nightly agent choosing among 5–50 overlapping personas sits in that hard zone. Expect it to **under-report** no-fit for truly novel sellers and to **over-report** no-fit for sellers with sparse data, with the rate moving whenever the prompt or model changes (ASSUMED) ([new-persona signal notes](../research_notes/Agent%20decides%20VANI%20persona/new_persona_signals.md)). PS07 already shows that the offline distance buffer catches *new observation*, not new needs: 64.8% of p95 misfits carry transcript or question signals against 8.1% of fitting sellers, and misfit outcomes are nearly identical (MF 9.9% vs 11.4%) (PROVEN) ([PS07 library prototype](../research_notes/Data%20derived%20persona%20library/ps07_library_prototype.md)).

**Three-run agreement buys accuracy at a large cost in coverage.** In 8,000 runs over 4 models, consistent tasks scored 82–87% and inconsistent ones 41–65%. **Answering only when 3 runs agree gave 87–88% accuracy at 54–62% coverage**, +6–14 pp over a single run. Consistency detected failures at AUROC 0.62–0.78, and single-run evaluation **misranked models 29.3%** of the time ([ICML 2026](https://icml.cc/virtual/2026/74530)). Agreement is a useful gate, not a truth signal, given the 28% shared-wrong rate above.

**Probabilities must be logged by code.** LLMs "do not robustly engage in exploration without substantial interventions" ([Krishnamurthy et al.](https://www.microsoft.com/en-us/research/publication/can-large-language-models-explore-in-context/)), and current LLMs largely fail in-context bandit tasks without algorithmic support ([EVOLvE](https://proceedings.mlr.press/v267/nie25b.html)). An off-policy evaluation of a real LLM coaching agent had to *approximate* logging propensities by fitting behaviour models or re-extracting token log-probs ([arXiv 2510.17173](https://arxiv.org/pdf/2510.17173)). Microsoft's Decision Service measured up to **3.0× estimation error from wrong probabilities and 8.7× from a decision leaking into features** ([arXiv 1606.03966](https://arxiv.org/abs/1606.03966)). Logs written by the agent itself are also suspect, since recent work reports that LLM agents can easily tamper with their own traces ([arXiv 2609.30266](https://arxiv.org/abs/2609.30266), title-level only). The probability, the draw and the decision row must therefore all be written by code.

## The merged design: the agent decides inside a code-computed fence

The merge takes Design L's decision authority and V2's surroundings. It drops V2's "baseline plus delta" framing in favour of per-candidate scoring by the agent, and it replaces both designs' self-reported no-fit with a computed signal. It reuses the V2 blocks unchanged: the B1 context builder, the B2 trait/state estimator, the B3 library, the B4 scoreboard, the B6 cook and the B12 data layer ([plan v2](../plans/VANI%20persona%20architecture%20plan%20v2.md)). **There is no rule table.** Rules appear only as seed values: the shrinkage weight α in the trait posteriors, the 28-day state decay, and 10–25 pseudo-call priors in scoreboard cells (Pega's StartingEvidence of 25 is the reference) ([Data driven persona agent report](Data%20driven%20persona%20agent.md)). Data overrides all of them.

| Step | Owner | What happens | Evidence basis | Logged |
|---|---|---|---|---|
| 1. Fence | Code | Eligible set: DNC removed, persona version published, voice exists for the start language, guardrails fixed. Scoreboard posteriors and trait/state estimates attached | Sierra guards; BCG batch guardrails | `eligible[]`, gate results |
| 2. Gather | Code, then agent | Code pre-fetches tool results (Salesforce "pre-reasoning context gathering"); the agent may call tools for more. Stats tools return n, CI, p_best; free-text tool returns masked spans with span ids | Krishnamurthy: summarised history needed; cost | `tool_calls[]`, snapshot id |
| 3. Decide | Agent (Sarvam-105b) | Scores **every** eligible persona 1–5 against a rubric, with `reason_code` and cited evidence; selects persona; writes plan (opening in native script, objection order, promoted branches, sensitivity within bounds). Scoreboard leader appears as one candidate, not as "the answer" | NOTA brittleness; anchoring (ASSUMED) | per-run scores, choice, reasons |
| 4. Agree | Code | Runs step 3 three times. Accept when ≥ 2 of 3 runs pick the same persona; require 3 of 3 to override a decisive scoreboard cell (p_best ≥ 0.95, none exist today) | ICML 2026 3-run agreement | `k_runs[]`, agreement rate |
| 5. Validate | Code | Every reason cites a tool field or free-text span id; code re-reads it and rejects mismatches. Existing checks: schema, no digits or price words in speech (FAQ Q5), greet-and-confirm first, confidence ≤ completeness (FAQ Q6). One repair call | CRITIC-style correction works because tools check; Confidence Dichotomy | validator results, repairs |
| 6. Draw | Code | Softmax over the agent's median fit scores, exploration floor per eligible persona, holdout share to P0; code draws and logs exact p. Off for judged demo sellers | Decision Service; 2510.17173 | `propensity`, `arm`, seed |
| 7. Fall back | Code | On disagreement or failed validation: code-only Thompson draw over the eligible set, logged as `path: fallback` | Plan v2 code-only path | `path` |
| 8. Flag | Code | No-fit computed, not asked (see below); seller still gets the best eligible persona at low confidence | NOTA and abstention papers | `fit`, `reason_code`, `missing_capability` |

Step 3 is where the team lead's design lives. The agent, not a formula, reads the seller's history and notes and decides. Per-candidate scoring replaces the open "pick one or NONE" question that the NOTA papers show is brittle. It also gives code the scores it needs for a logged draw and a no-fit threshold ([new-persona signal notes](../research_notes/Agent%20decides%20VANI%20persona/new_persona_signals.md)). Prompts must use a flat JSON schema: Sarvam's strict nested `json_schema` mode looped in 4 of 6 calls in an earlier spike, while a flat schema never failed (PROVEN) ([agent-as-decider notes](../research_notes/Agent%20decides%20VANI%20persona/agent_as_decider.md)). Pin model, prompt and tool-snapshot versions in the decision row. Keep all randomness for exploration in the code sampler so that p is exact. Sampling variance across the three runs is used only for the agreement gate.

**The no-good-fit signal is computed from three independent sources.** A seller is flagged when the agent's maximum fit score is ≤ 2 in at least 2 of 3 runs *with the same `reason_code`* (agent reason-code agreement). The flag is then cross-tabbed against the offline nearest-seller-type distance (beyond p95) and, once explored traffic exists, against an outcome gap: the seller's group does worse under every persona than comparable sellers do under their best one. The error sources are mostly independent, since distance errors come from data and coverage drift while agent errors come from prompts and models, so requiring agreement should cut false alarms (ASSUMED) ([new-persona signal notes](../research_notes/Agent%20decides%20VANI%20persona/new_persona_signals.md)). One path skips the distance requirement: a `missing_capability` reason (for example, a language or pace range no persona offers) is checkable against the catalogue, so agent agreement plus distinct-seller support suffices. "Insufficient data" is its own code and never counts as a new-persona vote. That blocks the PS07 failure mode where misfit tracked data coverage. The outcome-gap leg cannot run at the hackathon, because PS07 has one voice and one style (DOCUMENTED).

**New personas come from a weekly job, never from a single decision.** Every production category-expansion system found aggregates first. TnT-LLM summarises items, then generates, updates and reviews the taxonomy in minibatches. Human inter-rater κ was only 0.38–0.48, a warning that "is this a new category?" is itself subjective ([TnT-LLM](https://arxiv.org/html/2403.12173)). Clio extracts facets, embeds, clusters, names clusters with an LLM and applies a minimum-support threshold ([Clio](https://arxiv.org/pdf/2412.13678)). Amazon Lex surfaces missed utterances for human review ([Amazon Lex FAQ](https://aws.amazon.com/lex/faqs/)). The agent's short `reason_text` is the facet. The weekly job embeds it, clusters within each `reason_code`, and cross-tabs clusters against distance misfits and outcome gaps. An LLM then names each candidate and drafts its card. Code gates follow (ASSUMED initial values, to be tuned). Support must reach max(500, 0.5% of active) distinct sellers. The cluster must persist across 2 windows at ARI or Jaccard ≥ 0.7; the PS07 buffer reached only 0.54 between August and September (PROVEN). A coverage-matched misfit rate must reach at least 2× base. The delivery bundle must differ audibly from the nearest persona. A prompt or model change that moves the audit-sample no-fit rate by more than 2 pp freezes proposals for that window. A human approves with a rubric card. The new persona enters as an explored arm with a weak prior, and rejections are stored as known non-gaps so they are not proposed again.

**The cost is affordable if the agent re-decides only when inputs change.** With tool results pre-fetched into one call, three runs cost roughly three structured calls, about ₹0.5 per seller (ASSUMED from the PROVEN ₹0.16 per call). Sellers due a call whose snapshot, memory, library and scoreboard versions are unchanged since their last decision reuse it. The agent has already decided for them. A 1–2% random audit sample always re-runs, and it measures the agent's no-fit base rate and prompt drift. Distance-flagged sellers also always re-run ([new-persona signal notes](../research_notes/Agent%20decides%20VANI%20persona/new_persona_signals.md)).

## A pre-registered 40-seller test settles it before day 2

The comparison is cheap because all four arms run on one harness with configuration switches: anchor on or off, gates on or off, k = 1 or 3. Almost no build work is wasted, whichever arm wins.

The test set holds about 40 **synthetic** sellers built from aggregate patterns, with no real names or text. They fall into four strata. (a) Ten sellers carry structured signal only, which tests whether the agent does harm. (b) Ten carry free text that *changes* the right persona, which is L's claimed edge. (c) Ten carry distractor free text, such as a one-off remark, which tests over-reading. (d) Eight to ten are genuine no-fit cases, for example a Tamil-preferring seller when no persona has a Tamil voice, or a seller who needs a pace outside every version's range. Strata (a)–(c) double as planted known-fit profiles for the false no-fit rate ([new-persona signal notes](../research_notes/Agent%20decides%20VANI%20persona/new_persona_signals.md)). The scoreboard is seeded with prior-only cells and is identical for every arm.

Labels come first. **Before any arm runs**, two people who did not build the harness write the expected `persona_id` or "no fit" for each seller, plus 2–3 critical plan elements and a one-line rationale. These can be the team lead and the non-tech member. A third person adjudicates disagreements, and the report states inter-rater agreement. The label file is hashed and committed. Labels must not be derived from the estimator's seed values, which avoids the circularity of the earlier 23/23 test ([agent-as-decider notes](../research_notes/Agent%20decides%20VANI%20persona/agent_as_decider.md)).

There are four arms. The control is code-only: estimator plus scoreboard draw. Design L runs as specified, deciding with tools and self-reporting no-fit over the full library. Design V2 runs as baseline plus bounded change. The merged design runs as above. All arms use the same Sarvam model and identical tool snapshots, with **5 repetitions per seller per arm** (40 × 4 × 5 ≈ 800 runs; ≈ ₹250–500 at earlier measured prices, ASSUMED). Five repetitions follow from the 29.3% single-run misranking finding.

| Metric | Measure | Pre-registered use |
|---|---|---|
| Decision accuracy | Match to frozen label | Primary, per stratum |
| Free-text sensitivity | Accuracy on (b) | L's edge |
| Distractor robustness | Accuracy on (c) | Over-reading |
| No-fit precision / recall | On (d) and on (a)–(c) as planted fit | New-persona signal quality |
| Confident-wrong rate | Wrong with self-confidence ≥ 0.8 or run agreement ≥ 0.8 | Safety |
| Consistency | Agreement across 5 repetitions | Reproducibility |
| Citation validity | Share of cited fields/spans that check out | Grounding |
| Fallback rate, cost, latency | Per seller | Coverage and budget |

A judge model is used only for plan wording, never for persona choice. It must come from a different family than the decider, run on the internal gateway, be blind to arm and be calibrated on about 20 human-labelled items. LLM judges share errors with same-family deciders, and cross-provider shared wrong answers appear above chance ([alphaXiv 2607.08065](https://www.alphaxiv.org/abs/2607.08065.md)).

The decision rule is written into the label file before the run. **Adopt the merged design (agent selects) if it beats V2 on stratum (b) by ≥ 15 pp, is not worse than V2 or code-only by more than 5 pp on (a) and (c), has a confident-wrong rate ≤ V2's, and has no-fit F1 ≥ Design L's. Otherwise use the V2 framing (agent edits a baseline) with the same safeguards.** If unguarded Design L beats the merged design on (b) and loses nothing on (c), report it: that would mean the gates cost real accuracy. With 10 sellers per stratum, only differences of roughly 30 pp or more are reliably detectable, so treat the 15 pp threshold as a pre-commitment, analyse paired by seller (McNemar), and state the low power upfront. In parallel, M computes from PS07 aggregates the share of calls with a non-empty objection or summary. If that share is small, L's edge applies to few real sellers whatever the experiment shows. The schedule is labels and sellers this afternoon (about 2 h, in parallel with harness work), the batch run this evening, and analysis by 10:00 on day 2, before integration step 5 of plan v2.

## Devil's advocate

*"The merged design is V2 renamed."* Partly. With the same fence, validator and fallback, the two differ only in default and anchoring. That difference is real, though. The executed decision is the agent's unless a gate fails, the agent never sees a baseline it must argue against, and the experiment measures whether that matters. If stratum (b) shows no gain, the honest call is to switch to the V2 framing and say so.

*"Three-run agreement makes the agent decide only about half the time."* At the cited 54–62% coverage, code would fall back for roughly 40% of sellers ([ICML 2026](https://icml.cc/virtual/2026/74530)). That undercuts "the agent decides" as a headline. Two counters apply. Coverage on a 5-persona, well-described choice should be higher than on open benchmarks (ASSUMED, untested on Sarvam). And the fallback rate is itself a reported metric. If it stays above about 30%, either the rubric is unclear or the personas overlap, and both are library problems worth surfacing.

*"Agreement is not correctness."* True: 28% of cases were confidently wrong across every runner tested ([alphaXiv 2607.08065](https://www.alphaxiv.org/abs/2607.08065.md)). The cited-evidence validator and the pre-registered labels are the defence, not agreement alone.

*"A SQL query finds the only gap that matters."* If the one demonstrable new persona is "Tamil-preferring sellers, no Tamil voice", a language-demand-versus-catalogue query finds it with no LLM at all. Judges may then see the agent's no-fit as decoration. The agent's value is the *reason* attached to cases a query does not anticipate. Without real free text, that value cannot be shown at the event ([new-persona signal notes](../research_notes/Agent%20decides%20VANI%20persona/new_persona_signals.md)).

*"PS07 says there is nothing new."* Misfits are coverage artefacts with normal outcomes (PROVEN). A mechanism that proposes no new persona on real data is the correct result. Present it as "the guard worked" rather than forcing a candidate for the demo.

*"The scoreboard is empty."* Today the agent's "data" for VANI-side choices is designer priors, because PS07 had one style. The agent decides on seller-side evidence and free text. Any claim of lift waits for about 2,000 explored calls per arm per segment (ASSUMED arithmetic) ([plan v2](../plans/VANI%20persona%20architecture%20plan%20v2.md)).

*"No-fit votes become self-fulfilling."* If prompts or rubrics shift, personas get created. The audit-sample freeze and the "known non-gap" register guard this, at the cost of more process.

*"Free text cannot leave the premises."* Task A reads masked summaries. Until organisers rule, run the agent on the internal gateway or Sarvam and use synthetic sellers only.

*"Thresholds are invented."* The values 500 sellers, ARI 0.7, ≤ 2 pp drift, p_best 0.95 and the 15 pp decision margin are untested priors. Ship them as config, not as findings.

## Conclusion

The disagreement between the team lead's design and plan v2 is smaller than it looked, and it can be tested. Both designs need the same fence, because the evidence leaves no room for an ungated agent: inflated confidence, brittle "none fits" answers and unlogged randomness rule it out. Inside that fence, the agent should decide. Free-text history is the one signal that can change a VANI persona and that code cannot read. The open question is not authority but anchoring: does showing the agent a baseline suppress the changes free text should cause? The afternoon experiment answers it on VANI's own synthetic sellers rather than by argument.

The larger shift concerns new personas. The team lead's "no good fit" idea is the most original part of Design L, but its value is as a *reason facet* to aggregate, not as a trigger. Computed from agent reason-code agreement, distance and outcome gaps, then clustered weekly and approved by a human, it turns a noisy per-seller vote into a library change backed by evidence. That is what PS04's distinctness and evidence criteria reward. It also gives judges a clean story: the agent decides each seller, and code proves each decision.
