# Steer one Samvaad agent with a calibrated sidecar

The strongest architecture for the VANI "Seller-Fit Adaptive Voice Persona" build is **one single-state Sarvam Voice Agent whose behaviour is steered by a small set of agent variables**. The persona is set before dialling and adjusted live by a sidecar "signal server" that the agent calls as a tool on every seller turn. That server sends the latest turns to **TypeSafe Jev on OpenRouter's Decisions API**. Deterministic code then applies thresholds, hysteresis and priority rules, and returns a short directive plus an updated `seller_mode`. This shape follows from three platform facts. Sarvam has **no per-turn webhook**: the only automatic hooks are on_start and on_end, so a classifier can only enter the turn through an LLM-chosen tool call ([Sarvam API tool](https://docs.sarvam.ai/conversations/build/tools/https-tool)). **Multi-state agents are a legacy paradigm** due for end-of-life ([Sarvam multi-state](https://docs.sarvam.ai/conversations/build/states-conversation-flow)). And **voice, pace and speaker are fixed for the whole call** ([Sarvam speakers & voice](https://docs.sarvam.ai/conversations/build/voice-language)). Live adaptation therefore has to live in wording, brevity, empathy and language, while voice and pace become pre-call persona choices. The data supports this split. Static script personalisation went **0 for 3 in internal trials**. Rush shows up in **21% of calls and halves the meeting rate (13.6% vs 26.0%)**, 99% of the time first appearing mid-call. **46.6% of Tamil Nadu calls carry Tamil markers** while the bot speaks Hinglish ([internal validation](../../wiki/projects/vani-hackathon/persona-data-validation.md)). The notes also overturn several premises in the brief. Jev is not a chat-completions model. The in-call reply LLM cannot be an OpenRouter model, because Sarvam allows no bring-your-own LLM. Daytona's open-source repo is archived, and its low-tier sandboxes cannot reach sarvam.ai. Code Tools, the only deterministic steering path, are "available on request". The same harness (trace store, typed judges, paired simulated sellers) carries over almost unchanged to Quality Audit (#1) and Agent A/B Testing (#5). Persona design stays the leading candidate rather than a final choice.

## One agent, four variables, one sidecar server

The recommended system has six components. Only two of them run inside the live call path.

The **Sarvam Voice Agent** is the core. It is a single-state agent (Saaras v4 ASR, Sarvam's routed LLM, Bulbul TTS) whose instructions contain a fixed persona playbook. Each playbook section is keyed on variables (`seller_mode`, `persona_directive`, `language_pref`, `adapt_enabled`), plus one global rule: "call tool:read_seller_signal before every reply". Sarvam's harness reassembles "conversation history, variables, and available tools" on every turn, and tools "can read and write any agent variable mid-call". A variable written by the tool should therefore reach the LLM on the next generation step ([Sarvam harness](https://docs.sarvam.ai/conversations/build/concepts/harness); [Sarvam variables](https://docs.sarvam.ai/conversations/build/variables-personalization)). That last step is an inference that needs a day-1 check.

The **signal server** is an open-source FastAPI service, and it is the only thing the agent calls per turn. It receives the live Call Transcript, the call's interaction ID and the current variables. It builds a compact Jev state, calls Jev, runs the hysteresis state machine, and returns `{seller_mode, persona_directive, language_pref}`, which are mapped back into variables. A response template injects the directive as text the LLM reads.

The **persona generator** runs offline or just before dialling. It combines rules, seller archetypes and an OpenRouter LLM that fills only the soft text fields, under a JSON schema with per-field evidence. The **outbound launcher** calls Sarvam's Instant Outbound API with `agent_variables`, `app_version` and `initial_language_name` ([Sarvam create outbound](https://docs.sarvam.ai/conversations/api/instant-outbound/create)). The **simulated-seller harness** drives the same agent through `sarvam-conv-ai-sdk`. A **trace store and dashboard** receives two feeds: every signal-server decision in real time, and Sarvam's post-call webhook, which carries `final_agent_variables` and the transcript ([Sarvam outbound webhook](https://docs.sarvam.ai/conversations/api/instant-outbound/webhook-payload)).

The central design choice is that **persona is a variable, not a state**. Sarvam's own multi-state docs describe transitions that the agent judges "when conditions are met". No rule engine moves states based on variable values. Converting an agent to multi-state is "a one-way operation", and the paradigm "will reach end-of-life once multi-agent launches" ([Sarvam multi-state](https://docs.sarvam.ai/conversations/build/states-conversation-flow); [Sarvam conversation settings](https://docs.sarvam.ai/conversations/build/conversation-settings)). Peer platforms point the same way. Retell's deterministic "equation" transitions over dynamic variables and ElevenLabs' "Update state" plus expression edges are both variable-gated designs ([Retell transitions](https://docs.retellai.com/build/conversation-flow/transition-condition); [ElevenLabs workflows](https://elevenlabs.io/docs/agents-platform/customization/agent-workflows)). OpenAI Realtime lets instructions change at any time but locks the voice after the first audio output ([OpenAI Realtime guide](https://developers.openai.com/api/docs/guides/realtime-conversations)). Mutable register over a fixed voice is the industry norm, not a Sarvam handicap.

A second choice follows from the platform's model policy. Voice Agents "does not support bringing your own models at any part of the stack (ASR, LLM, or TTS)" and has no model picker ([Sarvam models](https://docs.sarvam.ai/conversations/build/models)). **OpenRouter LLMs therefore cannot write the agent's spoken replies.** They belong in four places: the persona generator, the seller simulator, the judges, and the teacher that labels data for calibrating Jev. The live directive should come from a **pre-written directive library**: short strings per mode and language, generated and reviewed offline with an OpenRouter model. Calling a chat LLM on the hot path would add 500–1,500 ms, and avoiding that cost is exactly why a Jev plugin was proposed for LiveKit ([livekit/agents #7355](https://github.com/livekit/agents/issues/7355)).

## Each seller turn pays one extra LLM step, so make Jev the cheap part

On every turn the agent's LLM decides to call `read_seller_signal`. Sarvam then POSTs to the signal server with the transcript "up to that point". The server answers, and the LLM runs a second pass over the tool result before Bulbul speaks ([Sarvam API tool](https://docs.sarvam.ai/conversations/build/tools/https-tool)). The classifier itself is fast. Jev measured **p50 108 ms and p95 159 ms** on TypeSafe's direct API ([jev-voice-turn README](https://raw.githubusercontent.com/dabit3/jev-experiments/main/jev-voice-turn/README.md)), p50 151 / p95 247 ms through a third-party gateway ([OrcaRouter](https://www.orcarouter.ai/blog/jev-typesafe-system-one-what-we-know)), and about 150 ms inside Pipecat ([Veris](https://veris.ai/blog/jev-turn-detection)). No OpenRouter-specific latency has been published. The expensive part is the extra LLM round-trip that any tool call forces. Industry budgets aim for **≤800 ms voice-to-voice**, and a single serial 300 ms tool call already pushes time-to-first-audio past 1.1 s ([Twig latency budget](https://www.twig.so/blog/voice-ai-agents-latency-budget-800ms)).

| Step (per seller turn) | Budget | Basis |
|---|---|---|
| Saaras v4 end-of-speech to final text | 100–150 ms | Saaras V4 streaming TTFT under 150 ms ([Sarvam blog](https://www.sarvam.ai/blogs/introducing-saaras-v4)) |
| LLM decides to call the tool (first pass) | 200–400 ms | Inference; not published by Sarvam |
| Sarvam egress to signal server and back | 40–100 ms | Inference; host the server in India |
| Jev via OpenRouter Decisions API | 150–300 ms, hard deadline 350 ms | Direct and gateway measurements above |
| Calibration, hysteresis, directive lookup | <5 ms | In-process code |
| LLM second pass over tool result to first token | 300–500 ms | Inference |
| Bulbul TTS time to first byte | 100–250 ms | Industry budget ([Twig](https://www.twig.so/blog/voice-ai-agents-latency-budget-800ms)) |
| **Added by adaptation** | **~0.7–1.2 s** | The cost of the tool call, mostly LLM passes |

This budget leads to a three-mode design with an explicit switch rule. In **synchronous mode** (the default), the server waits for Jev up to the deadline. If Jev answers, the directive applies to the reply to the *current* seller turn. That matters because a rushed seller who gets a long reply on the very turn they said "jaldi bolo" is exactly the failure the data shows. If Jev misses the deadline, the server returns the last committed mode and finishes classifying in the background, so the result lands on the next turn. This mirrors the "app never stalls" fail-safe in the jev-voice-turn code ([jev-voice-turn README](https://raw.githubusercontent.com/dabit3/jev-experiments/main/jev-voice-turn/README.md)). **Next-turn mode** always returns the cached decision instantly and classifies asynchronously. It saves only the Jev slice, because the LLM's extra pass remains. **Checkpoint mode** is the fallback if the day-1 measurement shows a per-turn overhead p95 above about 800 ms. The agent calls the tool only at pitch checkpoints (after the opener, after the value proposition, on any objection), and Sarvam's native auto-detected language switch covers language.

Two mechanisms partly hide the latency. If Code Tools are granted, their `pre_run_message` speaks a short line before the tool runs ([Sarvam code tools](https://docs.sarvam.ai/conversations/build/tools/code-tools); [sarvam-conv-ai-sdk](https://pypi.org/project/sarvam-conv-ai-sdk/)). A one-word "ji" is a passable acknowledgement but becomes grating if used every turn. With API tools, Sarvam documents no automatic filler, so silence is the default assumption.

The second reliability risk is compliance. Whether the routed LLM actually calls the tool every turn is probabilistic. The tool therefore persists `seller_mode` in a variable, so a skipped turn keeps the previous persona. Temperature sits at the 0.1 "Compliant" end. Every skipped turn is counted, because the server knows the turn index it should have seen.

## The persona is fixed before dialling; only its register moves live

The per-call flow begins well before the phone rings. A **hard gate** removes `do_not_call_requested` sellers and routes `already_in_touch_with_executive` sellers to a confirm-not-pitch archetype. The **persona generator** then assembles a compact JSON spec. Each field carries an `evidence` list that cites the seller feature and rule that produced it, which directly answers the judging criterion "support from past-call evidence". The **launcher** maps that spec onto Sarvam's surfaces: `agent_variables` (archetype, formality, hinglish_ratio, objection order, disclosure flag, `adapt_enabled`), `initial_language_name`, `initial_bot_message`, and `app_version` in the Instant Outbound body ([Sarvam create outbound](https://docs.sarvam.ai/conversations/api/instant-outbound/create)). The speaker comes from Sarvam's per-language voice mapping for the starting language. It then stays fixed even if the caller switches language ([Sarvam conversation settings](https://docs.sarvam.ai/conversations/build/conversation-settings)).

Instant Outbound accepts no TTS override ([Sarvam create outbound](https://docs.sarvam.ai/conversations/api/instant-outbound/create)). The only per-session TTS override sits on the SDK session config or in an on_start **code** tool (`text_to_speech_config` with speaker, pitch, pace and volume) ([sarvam-conv-ai-sdk](https://pypi.org/project/sarvam-conv-ai-sdk/)). For the live phone demo, the practical lever for a persona-specific pace is therefore an **agent version per pace profile**, for example "crisp" at 1.1× and "warm" at 0.95×, selected through `app_version`. That is an inference from the API shape and needs to be confirmed. The simulated-seller demo can set voice and pace per session directly through the SDK.

### Rules decide hard fields, archetypes decide defaults, the LLM writes only prose

The generator is a three-layer hybrid. **Rules** own every field that carries compliance stakes or strong evidence: start language, DNC handling, up-front AI disclosure when `asked_if_talking_to_bot` is set, escalation routing, and the starting pace and eagerness for sellers with past rush or frustration. **Archetypes** supply the defaults. They come from clustering the PS07 seller file into 4–6 groups on the traits with the widest meeting-rate spreads: turnover (9.7 points), business type (7.1) and nature of business (6.3) ([internal validation](../../wiki/projects/vani-hackathon/persona-data-validation.md)). The working set has six members: busy established manufacturer, small trader, regional-language seller, previously frustrated or bot-sceptic, already engaged with an executive, and thin-profile neutral. The thin-profile archetype matters because missing-profile sellers convert highest (~14–18%), so over-adapting to them is a risk ([internal validation](../../wiki/projects/vani-hackathon/persona-data-validation.md)). An **OpenRouter LLM** fills only the soft text: opening wording chosen from at most four templates, objection phrasing in the order set by `past_objections`, and the rationale shown to judges. Every output passes a strict JSON schema.

The design leans on accommodation rather than content because the evidence does. Wharton studies found that slowing speech from 5.22 to 4.63 syllables per second, still within the normal range, raised satisfaction by **7.1%** ([Knowledge at Wharton](https://knowledge.wharton.upenn.edu/article/how-speaking-slower-influences-consumer-behavior/)). Internal personalised-content trials, by contrast, lost to control: 14.8% vs 17.8%, 11.1% vs 15.8%, and 3.3% vs 18.4% ([internal validation](../../wiki/projects/vani-hackathon/persona-data-validation.md)). One trial did cut Not Interested from 13.1% to 5.5%. The personalised opener earns attention, and the close is where it fails. The objection playbooks therefore follow Gong's 300M-call taxonomy: dismissive (49.5%), situational (42.6%) and existing-solution (7.9%). Each is handled with agreement, a question, and a low-commitment "test drive" offer, here a meeting slot ([Gong Labs](https://www.gong.io/resources/labs/we-found-the-top-objections-across-300m-cold-calls-heres-how-to-handle-them-all/)).

Generator quality is measured on two axes. **Fit** is scored by an OpenRouter judge from a different model family than the generator, which also checks that every evidence claim cites a real feature value. **Distinctness** is measured by field-level Hamming distance between archetypes, the silhouette score of the clusters, and side-by-side audio of the same line spoken in three personas.

### Language is a separate axis that starts native and never flips on one loanword

The language policy is a state rule table overridden by history. TN starts in ta-IN, GJ in gu-IN with Hinglish on standby, AP/TS in te-IN, KA in kn-IN, KL in ml-IN, WB in bn-IN, and the Hindi belt and MH in Hinglish. A seller whose past transcripts carry regional markers overrides the state default. Allowed languages are always the start language plus Hindi and English, with Sarvam's Language Switch core tool and auto-detect (with its "Switch after" delay) enabled ([Sarvam core tools](https://docs.sarvam.ai/conversations/build/tools/core-tools); [Sarvam conversation settings](https://docs.sarvam.ai/conversations/build/conversation-settings)).

Starting in the native language matters more on Sarvam than elsewhere. The speaker locks to the *starting* language, so a call that opens in Hinglish and later switches to Tamil keeps a Hindi-mapped voice speaking Tamil ([Sarvam speakers & voice](https://docs.sarvam.ai/conversations/build/voice-language)). Bulbul covers 11 languages while Saaras understands 22, so sellers speaking Assamese, Urdu and similar languages fall back to Hinglish or English ([Bulbul model page](https://docs.sarvam.ai/api-reference-docs/getting-started/models/bulbul); [Saaras model page](https://docs.sarvam.ai/api-reference-docs/getting-started/models/saaras)). Language should also be framed as an opportunity rather than a pain signal: calls with regional language reach **31.4% meeting-fixed vs 23.2%** without ([internal validation](../../wiki/projects/vani-hackathon/persona-data-validation.md)).

Live switching uses three triggers. The first is two consecutive seller turns in a non-current language, each at p ≥ 0.7. The second is an explicit request ("Tamil-la pesunga", "Gujarati ma bolo"). The third is repeated confusion while the call is in Hinglish, which makes the bot *offer* the regional language. After a switch, the bot never switches back within three turns. Script handling has a known gap. Internal transcripts are romanized (0.2% Devanagari) ([internal validation](../../wiki/projects/vani-hackathon/persona-data-validation.md)), but Sarvam's post-call webhooks carry an English `en_text` rendering ([Sarvam outbound webhook](https://docs.sarvam.ai/conversations/api/instant-outbound/webhook-payload)). The transcript a tool receives mid-call could be translated in the same way, which would erase the language cues the classifier needs. Until a test call shows the format, the tool should also read the `language_name` variable.

A few smaller settings complete the language layer. "Important words" (ASR hotwords) take "IndiaMART", the product names and the seller's top categories per call ([Sarvam conversation settings](https://docs.sarvam.ai/conversations/build/conversation-settings)). Bulbul pronunciation dictionaries fix brand pronunciation. The deck claims "pace plus wording" adaptation and does not claim pitch or emotion control, because Bulbul does not support SSML ([Bulbul model page](https://docs.sarvam.ai/api/getting-started/models/bulbul)). Bulbul V4 reached Voice Agents only on 2026-10-06, and its style controls are undocumented for agents ([Sarvam changelog 2026-10-06](https://docs.sarvam.ai/changelog/2026/10/6)).

## Jev asks eight English questions and code decides the switch

Jev is reached through `POST https://openrouter.ai/api/alpha/decisions` with a body of `{model, state, questions}`. **It is not a chat-completions model**, and "chat completions SDKs will not work with it" ([OpenRouter Jev guide](https://openrouter.ai/docs/guides/community/jev)). The separately listed `typesafe/jev-router` is a model-selection router for chat requests, not a signal classifier ([RuntimeWire](https://runtimewire.com/article/typesafe-jev-router-openrouter-launch)). Jev offers three answer types: `noul` returns only P(yes) with no confidence field, while `choice` and `score` return probabilities and a confidence. All questions in one request run in parallel and cannot see each other's answers ([OpenRouter Jev tutorial](https://openrouter.ai/docs/guides/community/jev-tutorial); [TypeSafe API](https://docs.typesafe.ai/api.md)). At **$0.042 per million input tokens with free output**, a ~1,200-token decision costs about $0.00005, under $0.001 per call ([TypeSafe models](https://docs.typesafe.ai/models.md)). Cost does not constrain the design.

The **state** sent per seller turn holds call metadata (turn index, elapsed time, current persona and language, pitch stage), the last 3–4 turns, the latest seller turn in its own field, and simple features such as word count. It also carries an optional `regional_markers_found` list from a deterministic lexicon. TypeSafe warns that "accuracy falls as the state grows with content unrelated to the decision" ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)), so the pitch script, catalogue and seller profile stay out. The agent's previous line stays in, so that "kya?" after a garbled bot line is not read as genuine confusion.

The **questions** are written in English, because "English is the primary training language and where accuracy is currently best" ([TypeSafe models](https://docs.typesafe.ai/models.md)). Romanized Hinglish, Tamil and Gujarati cue phrases go inside the criteria text, and counter-examples go in the false criteria. Six of the eight questions are Nouls: `rushed`, `frustrated`, `confused`, `bot_question`, `interested` and `opt_out`. Nouls fit because a seller can be rushed and interested at once, and one independent test found the Score type poorly calibrated (44.7% accuracy at a mean stated probability of 0.74) ([OrcaRouter](https://www.orcarouter.ai/blog/jev-typesafe-system-one-what-we-know)). Two are Choices with explicit escape options. `language` takes hinglish, hindi, english, tamil or gujarati, plus `other_unclear`. `next_persona` lists `keep_current` first. The same source found that without an escape option, 0 of 30 out-of-scope messages were flagged ([OrcaRouter](https://www.orcarouter.ai/blog/jev-typesafe-system-one-what-we-know)). Option order is fixed and never shuffled, because order affects Choice answers ([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)). Jev's `next_persona` answer is only advisory and logged. A deterministic mapping from signals to persona is what actually acts, because it is auditable. Seller speech is untrusted input, so transcript text goes only in `state` and never in `instructions`.

### Events fire once; states need to persist before the persona flips

The decision policy treats some signals as events and others as states. **Events** (`opt_out` ≥ 0.90, `bot_question` ≥ 0.80) fire on a single turn without hysteresis. Opt-out ends the call with an apology and a suppression flag. A bot question gets a truthful, verbatim disclosure ("Main IndiaMART ki AI assistant hoon"), then a four-turn cooldown, after which the prior persona resumes. **States** run a Schmitt trigger on an EMA (α ≈ 0.6) with a minimum dwell of two agent turns, at most two non-language switches per call, and a fixed priority order. Persistence is mandatory for seller turns under three words, because short imperatives score unreliably ([jev-voice-turn README](https://raw.githubusercontent.com/dabit3/jev-experiments/main/jev-voice-turn/README.md)). Jev timeouts, 429s, 529s and malformed answers all resolve to "keep current". At most one request is in flight per call, and stale answers are discarded.

| Signal | Enter | Exit | Persona effect (wording only) | Rationale |
|---|---|---|---|---|
| rushed | p ≥ 0.80, or EMA ≥ 0.70 on 2 turns | EMA ≤ 0.40 on 2 turns | ≤15-word turns, skip pleasantries, offer a fixed callback or meeting slot | 21% prior, meetings halve; cheap to act |
| frustrated | p ≥ 0.75 | EMA ≤ 0.35 | One apology, calm register, short exit or human callback | Rare (3.6%) but costly to miss |
| confused | p ≥ 0.80 | EMA ≤ 0.40, auto-decay after one clarification | Restate purpose in one simple sentence, step by step | Separate it from interest-driven questions |
| interested | p ≥ 0.85 | EMA ≤ 0.50 | Move to concrete slot offer | Combine with rushed → crisp slot offer, no pitch |
| language | Same non-current language 2 turns at p ≥ 0.7, or explicit request | No switch-back within 3 turns | Native-language directive; Sarvam Language Switch | Orthogonal axis; never fights style |

The priority order is opt_out > frustrated > bot_question > rushed > confused > interested, with language applied independently on top. These thresholds are **engineering priors**. No published voice-agent study gives optimal enter/exit values, and TypeSafe's own guidance is "start with conservative thresholds, test with your own data, and adjust" ([TypeSafe confidence](https://docs.typesafe.ai/confidence.md)). Over-eager control carries a measured cost. In Veris's test, Jev-driven turn-holding cut talk-over from 52% to 11% but raised median reply latency from 2.1 s to 4.6 s, with task success flat ([Veris](https://veris.ai/blog/jev-turn-detection)).

### Calibration replaces training, because Jev cannot be fine-tuned

"Jev is not fine-tuned or LoRA-adapted with customer data". Customisation happens only through `state`, `instructions` and `criteria` ([TypeSafe models](https://docs.typesafe.ai/models.md)). TypeSafe claims Jev is calibrated by construction, but one secondary study found out-of-distribution ECE of 0.107 on synthetic tickets against 0.024–0.032 on public benchmarks ([OrcaRouter](https://www.orcarouter.ai/blog/jev-typesafe-system-one-what-we-know)). Romanized, code-mixed seller speech is squarely out of distribution, and no published Jev accuracy exists for Hindi, Tamil or Gujarati.

The calibration loop has seven steps:

1. **Sample.** Draw about 6K seller turns from the historical corpus: half uniformly at random, half enriched for rare signals using the keyword heuristic or a first Jev pass, with importance weights.
2. **Label with teachers.** Two OpenRouter teacher models label each turn, using rubrics worded identically to the Jev criteria. Items where the teachers disagree go to humans.
3. **Build a gold set.** Two native-speaker annotators label 300–500 turns, oversampling Tamil and Gujarati. Signals where the annotators' Cohen's κ falls below about 0.6 get their definitions rewritten.
4. **Tune criteria wording.** Sweep instruction and criteria variants on the dev split and keep the variant with the best PR-AUC per signal. Each sweep costs about $0.30. Wording dominates accuracy: one test reported 95.9% with good criteria against 16.7% with wrong ones ([OrcaRouter](https://www.orcarouter.ai/blog/jev-typesafe-system-one-what-we-know)).
5. **Calibrate.** Fit isotonic or Platt calibrators per signal and per language bucket ([scikit-learn calibration](https://scikit-learn.org/stable/modules/calibration.html); [Guo et al. 2017](https://arxiv.org/abs/1706.04599)).
6. **Choose thresholds and replay.** Pick thresholds from precision targets (about 0.85 for rushed, 0.7 for frustrated). Replay whole calls through the state machine to measure switches per call, flaps and time-to-detect.
7. **Iterate on the uncertain band.** Run two or three active-learning rounds on turns in the 0.35–0.75 band.

For the hackathon itself, this collapses to a **100-turn-per-language smoke test against the teacher** on day 1. Pin `typesafe/jev-1.13` so the calibrators stay valid.

## Paired simulated sellers turn a demo into a causal estimate

No open-source simulator drives a Sarvam Samvaad agent out of the box. chanl-eval (MIT) is text-only, with OpenAI-compatible adapters. Egma (MIT) ships LiveKit and Retell adapters. Pipecat's release-eval harness (BSD-2) is the closest model, with an LLM caller that "hangs up when the goal is reached or clearly out of reach", TTS audio mode and `--repeat` runs ([chanl-eval](https://github.com/chanl-ai/chanl-eval); [voiceaispace Egma](https://www.voiceaispace.com/tool/egma-ai); [Pipecat evals README](https://github.com/pipecat-ai/pipecat/tree/main/evals/release)).

The recommendation is a thin custom Python harness. An OpenRouter LLM plays the seller from a persona card. Bulbul TTS renders the seller's lines as 16 kHz PCM, which is streamed into the agent with `send_audio` in CALL mode. The agent's lines arrive through `transcript_callback` (role=bot), so the seller LLM needs no STT ([sarvam-conv-ai-sdk](https://pypi.org/project/sarvam-conv-ai-sdk/)). For fast, silent iteration, the SDK's undocumented `send_text` with CHAT interaction type is worth testing. Sarvam's built-in **Tests** feature, a simulated user plus an AI judge for up to 20 runs per case through a REST API, is a cheap regression complement but cannot run seeded, scripted, paired voice arms ([Sarvam changelog 2026-09-17](https://docs.sarvam.ai/changelog/2026/9/17)).

Persona cards are built from the historical corpus, not invented. Each card holds segment, language and code-mix ratio, patience budget, rush level, a frustration curve, a verbosity target sampled from real turn-length distributions, objections with their earliest turn and probability, a hidden goal, and a hang-up rule. The `evidence_refs` field points to cluster IDs, never raw calls. This grounding matters because LLM simulators drift toward "excessive verbosity… and unreasonable patience" ([ConvApparel](https://arxiv.org/html/2602.16938v1)) and abandon their assigned personas ([arXiv 2511.00222](https://arxiv.org/abs/2511.00222v1)). Realism is checked three ways: distributional matching of turn and call length and objection frequency, an LLM discriminator that should score near 50% at telling real from simulated transcripts, and an EVA-Bench-style filter that discards runs where the simulator broke character ([EVA-Bench](https://arxiv.org/abs/2605.13841)).

### The control arm must call the same tool, or latency confounds the lift

The experiment is a within-card crossover. Each persona card, seed and **scripted event schedule** (for example, rush injected at seller turn 3, a Tamil reply at turn 5) runs once with `adapt_enabled=ON` and once with it OFF. Arm order is randomised and the arms are interleaved in time.

The OFF arm must still call `read_seller_signal` and still run Jev, with the server returning a neutral directive. This choice is subtle but decisive. A control arm with no tool call would answer roughly a second faster per turn, and any lift would then be confounded with latency. The OFF arm also logs Jev's view of the seller, which gives a signal-timing baseline for free. An optional third arm, **"prompt-only"**, tells the agent to detect rush and confusion itself, with no classifier. This is the steelman alternative. If Jev-plus-hysteresis beats it, the sidecar has earned its latency.

The budget is **20–30 cards × 3 seeds × 2 arms, or 120–180 voice calls**. With 10–20 parallel sessions that is roughly 30–60 minutes of wall-clock time. Results are paired differences with a bootstrap CI that resamples cards (not calls), plus a Wilcoxon or sign test. About 15 pairs detect a large effect (d = 0.8) and about 34 a medium one (d = 0.5). A binary meeting-fixed proxy is weak at this N: 30% vs 50% needs roughly 80–100 pairs. Continuous judge scores and objective timing therefore lead the analysis.

The most jury-proof metric is **switch latency against the scripted trigger**, measured in turns and seconds. It needs no judge, because the harness knows exactly when rush was injected. The **false-switch rate** comes from the same script. Persona-fit and naturalness judges use OpenRouter models from a different family than the seller simulator, with the arm label hidden and positions swapped, calibrated against 30–50 human-labelled calls ([Zheng et al.](https://arxiv.org/abs/2306.05685)). Jev should **not** judge switch correctness in the ON arm, because it made those decisions, and evidence shows that when Jev is confidently wrong, LLM judges usually share the error ([arXiv 2609.29769](https://arxiv.org/abs/2609.29769)). Reliability is reported as pass^k alongside pass@1, because the two diverge sharply (median gap 0.44 in EVA-Bench) ([EVA-Bench](https://arxiv.org/abs/2605.13841)). A positive result is lift on the *simulated* population. Live A/B testing is the external-validity step, and the deck should say so.

### Daytona fits the dashboard, not necessarily the Sarvam client

Daytona's public repo was **archived on 3 Oct 2026**, and core development has been private since June 2026. The last open release, v0.190.0, is AGPL-3.0, and the community fork Nightona continues that code ([GitHub daytonaio/daytona](https://github.com/daytonaio/daytona); [Nightona README](https://cdn.jsdelivr.net/gh/nightona-co/nightona@main/README.md)). Tier 1 and 2 sandboxes have restricted egress that "cannot be overridden". Their allow-list includes `openrouter.ai` but **not sarvam.ai** ([Daytona network limits](https://www.daytona.io/docs/en/network-limits/)). Tier 3 requires a $500 top-up ([Daytona limits](https://www.daytona.io/docs/en/limits/)).

That leaves three options. The first is a sponsored or Tier 3 org with full egress. The second is self-hosted Nightona. The third splits the work: OpenRouter seller LLMs, judges and the dashboard run inside Daytona, while the SDK client that streams to Sarvam runs on a laptop or VM. Ask the organisers first. Preview URLs work on any port and can carry signed, expiring tokens ([Daytona preview](https://www.daytona.io/docs/en/preview-and-authentication/)). That makes a sandbox a workable public host for the signal server, because Sarvam API tools can send the `X-Daytona-Skip-Preview-Warning` header. WebSocket upgrade through preview URLs is undocumented. In the deck, describe Daytona as "last AGPL-3.0 release; community fork Nightona", not as plainly open source.

## The live phone call needs KYC, a rented number and a TRAI check

Instant Outbound places a single call without a campaign. It needs a `connection_id` and an agent number, and the simplest source is **Rent from Sarvam** (Vobiz-backed), which requires KYC before any number can be rented and is billed from the Sarvam wallet ([Sarvam rent a number](https://docs.sarvam.ai/conversations/deploy/telephony/rent-from-sarvam)). User Identifier is empty on outbound calls, so seller context travels entirely in `agent_variables` ([Sarvam API tool](https://docs.sarvam.ai/conversations/build/tools/https-tool)). The webhook's documented failure reasons include "Phone number is registered under TRAI NDNC" ([Sarvam outbound webhook](https://docs.sarvam.ai/conversations/api/instant-outbound/webhook-payload)), so check the presenter's number in advance.

TRAI's amendment dated 18 Sep 2026 treats AI-voice calls as A2P calls that must be **pre-declared to the telecom provider**, with CLI details ([TelecomLead](https://telecomlead.com/telecom-services/trai-tightens-spam-call-rules-with-ai-ml-detection-%E2%82%B90-05-a2p-charge-and-faster-enforcement-127804)). Whether Sarvam or Vobiz handles that declaration for rented numbers is unknown. Ask on day 1 and get the presenter's explicit consent.

During the call, the signal server streams every decision to the dashboard over SSE. Judges then watch P(rushed) cross its threshold and `seller_mode` flip as the presenter says "jaldi bolo". That live view is more persuasive than Sarvam's Log Analyser CHANGED badges, which appear only after the fact.

Three further risks matter. The first is Jev quality on romanized Tamil and Gujarati, for which no published data exists. The mitigation is the lexicon pre-feature, the per-language smoke test and a teacher-model fallback for offline labels. The second is cost and quota. ## The same trace-and-judge spine becomes Quality Audit and A/B testing

Everything above is one pipeline: a call (simulated or real) produces a trace, typed judges score it, and an aggregator analyses the scores. Only the input and the aggregation change between problems.

For **Quality Audit (#1)**, the judges point at real VANI calls. Sarvam's post-call webhooks already deliver transcripts and final variables, and Jev's typed questions run at a fraction of LLM-judge cost: 16–325× cheaper and 28–350× faster at similar accuracy on binary criteria ([arXiv 2609.29769](https://arxiv.org/abs/2609.29769)). That makes auditing every call affordable. On top of this sit Fatal/Non-Fatal severity per criterion and clustering of judge rationales to find root causes. Fixes are validated by regenerating persona cards from failing calls and running fix ON vs OFF through the paired simulator. That is the fix loop Egma pairs with production monitoring ([voiceaispace Egma](https://www.voiceaispace.com/tool/egma-ai)).

For **Agent A/B Testing (#5)**, the persona ON/OFF experiment *is* a two-arm test. Variants become `app_version`s in Instant Outbound. Paired simulation gives a high-power pre-flight with few calls. Live traffic then uses always-valid mSPRT p-values, or a Beta-Binomial posterior, so the team can monitor continuously and stop early without inflating false positives ([Johari et al.](https://arxiv.org/abs/1512.04922v2)). A one-sided guardrail on the Fatal rate sits alongside. chanl-eval's `compare --prompt-a --prompt-b` shows the same shape in open source ([chanl-eval](https://github.com/chanl-ai/chanl-eval)).

Persona remains the leading candidate because it alone makes the voice itself the demo. If day-1 spikes 2 and 5 fail badly, the trace store, judges and harness carry over to #1 or #5 with little rework.

## Conclusion

The research changes what "adaptive persona" can honestly mean on Sarvam. It is not a voice that morphs mid-call. It is a fixed voice chosen well before dialling, in the seller's language at a fitting pace, whose *words* get shorter, calmer, plainer or more transparent within one turn of a calibrated signal. The engineering risk has also moved. Jev's ~150 ms is no longer the bottleneck. The bottleneck is the extra LLM pass that Sarvam's tool-only integration forces, and whether the routed LLM reliably makes that call, so spikes 2 and 3 decide the build more than any modelling choice.

The most valuable design decision is quieter: the control arm keeps the tool call and Jev running and only neutralises the directive. That one choice turns a persuasive demo into a defensible causal estimate. It also makes the persona build a working prototype of the A/B engine (#5) and the audit judge stack (#1). Whichever problem the team finally picks, most of the first day's work carries over.
